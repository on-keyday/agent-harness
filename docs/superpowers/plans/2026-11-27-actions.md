# Actions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The server keeps named command templates (actions). An `ActionSet`-conditioned `exec_run` runs exactly those, and nothing else. An action can be edited only by someone who could re-grant every holder of it.

**Architecture:** Definitions live in a new store, `<data-dir>/actions.json`, beside the runner-key store. They are validated by a new pure package, `actiondef`, which the server, the CLI and the wasm build share. An `exec` that names an action is resolved on the server to an argv, and goes on to the runner as the existing `RunnerExecRunRequest`. So no runner-decoded format changes (C8). The `exec_run` dispatch gate checks the target without the condition. Once the body is read, the object gate decides: `authorizeObject` with the action id, or `inScope` for a raw argv, which reaches nothing through a conditioned bit (C7).

**Tech Stack:** Go, `.bgn` → `make protoregen`, wasm (`cmd/harness-webui-wasm`), WebUI JS.

**Spec:** `docs/superpowers/specs/2026-11-26-grant-conditions-and-bound-enrollment-design.md`. This plan covers:
- C8, C10–C13, C16 and C17;
- § Actions;
- § Surfaces: the action verbs, the action variant of exec, and the overlap warning;
- the C11, C12 and C7-object lines of § Testing, plus the action half of its dummy E2E.

This is the third of three plans. Grant conditions and bound enrollment are already on this branch. Plan 1 deferred two things to this plan (its ledger, Task 7): the README docs and the agent-skill docs for `--grant-condition`.

## Global Constraints

- **Limits** (§ Actions, Wire). All are checked in `actiondef.Validate` and nowhere else:
  - action name `[a-z0-9][a-z0-9._-]{0,63}`, unique across the store;
  - param name `[a-z][a-z0-9_]{0,31}`, unique in its definition;
  - 0–16 params;
  - 1–64 template elements, and element 0 is a literal (C17);
  - 1–32 choices per `choice` param;
  - a literal is 1–4096 bytes with no NUL;
  - a description is 0–1024 bytes.
- **Ruling, a choice literal fits its value:** a choice literal is at most 255 bytes, because `ActionValue.len :u8` must be able to carry it. Edit the spec's ActionParam comment to say so.
- **`token`** (C12): 1–128 bytes of `[0-9A-Za-z._-]`, not starting with `-`. It is fixed code (`actiondef.ValidToken`); no pattern is supplied by anyone.
- **An action run** (C12, C17):
  - each parameter value is exactly one argv element;
  - `pty = 0`, `shell_line = 0`, `sshd_parent = 0` and `stdin_enabled = 0`, whatever the request carried;
  - `term` is ignored.
- **Ids and revisions:**
  - An `ActionID` is 16 bytes from `crypto/rand` (C16). All-zero means "create" in `ActionPutRequest`.
  - An edit names `expect_revision`. A mismatch answers `stale_revision`, and nothing is written.
  - An invocation does not pin a revision.
- **The store file** holds native JSON fields (name, params, template, …), never encoded wire bytes. A file that does not parse is a startup error, as `runner-keys.json` is.
- **`action_admin = 0x100000000`**, and `all` widens to `0x1ffffffff` (§ Actions, Wire). The WebUI touches bits only through `capHas` / `capOr` / `capXor` (53-bit budget).
- **The three gates (C13):**
  - `action_put` and `action_remove` need `action_admin`, as a central gate;
  - `action_list` needs `action_admin` OR `exec_run`;
  - all three are `noTarget`.
- **Out of reach is not an oracle:** answer as for an unknown id. Every caller that passes the list gate sees every action. Definitions are server configuration, not per-task objects, so the spec's "one the caller may not see" names an empty set in this round.
- Wire changes are appended only. Run `scripts/wire-skew-check.sh` after the wire commit. Use `make test`. Stage by explicit path. Do not land.

**Plan decisions to check** (each is a spec edit in Task 1 or Task 4):
- **(a)** `ExecRunStatus` gains `no_such_action` and `outside_condition`. The spec says "missing → `not_found`", but the CLI reads `not_found` as "task not found". That would misreport the spec's own § Testing case ("deleting an action makes exec_run of it refused"). Neither new status is an oracle: both are answered only after the target passed the scope gate (condition ignored).
- **(b)** C11's "what `schedule edit` of that schedule needs" is read as:
  - the editor's `exec_run` is unconditioned;
  - the editor passes `scheduleReach` and `schedulePower(cid, &sc, "")`;
  - the editor is not the schedule's own task;
  - `storedGrant` accepts the schedule's stored grant, rewritten unchanged with the editor as granter. That is exactly the gate a flag-less `schedule edit` by the editor runs (S-D16).
- **(c)** `--grant-condition exec_run=actions:…` keeps taking full 32-hex ids. It does not take names: resolving a name needs a connection, which the pure parser does not have. `action ls` prints the full ids to copy from.

## Review Focus

- **A raw argv reaching a conditioned `exec_run`.** Moving the dispatch gate to "condition ignored" makes `openExecRun` the only thing that stops it. Every raw-argv path (CLI `exec`, the ssh gateway, the TUI, the WebUI) goes through that one function. Pinned in Task 5: `TestRawArgvRefusedOnActionSetConditionedExecRun`.
- **A parameter value that reads as an option, or as shell.** A value with a space, a `;` or `$(…)` must reach the runner as one argv element with `shell_line = 0`, even when the request asked for `shell_line = 1` or `pty = 1`. Pinned in Task 5: `TestActionRunForcesFlagsAndOneElementPerValue`. The leading `-` is refused for a token in Task 2.
- **An editor who is itself a holder,** or who is a holder only through a finished task or a schedule. The edit must be refused, and the definition and revision left unchanged. Pinned in Task 4: `TestActionEditRefusedForSelfHolder`, `TestActionEditRefusedForFinishedHolderOutsideReach`, `TestActionEditRefusedForScheduleHolder`.
- **A store file lost or rolled back.** A new action with the old name gets a new id, and a grant naming the old id must not run it. Pinned in Task 5: `TestRecreatedActionIsNotTheOldGrant`.
- **The inline answer of `action_put` growing past one datagram.** Its `message` is the one variable-length inline field this plan adds. The server cuts it to 256 bytes. Pinned in Task 4: `TestActionPutResponseFitsADatagram`.


`actionEditRefusals` works as follows:
- The operator always passes.
- The holders are:
  - every task in `h.Tasks.List(0)`, whatever its status, whose `Scope.NamesAction(id)`;
  - every schedule in `h.Sched.Store.List()` whose `Grant.Scope.NamesAction(id)`.
- An editor that is one of the task holders gives `selfHolder`.
- A task holder counts as refused unless it passes both:
  - `regrantReaches(cid, holder)` (R1);
  - `execRunCovers` (R2): the caller holds `exec_run`, its own `exec_run` condition is nil, and its target set ⊇ `authority.ActionSet(holder.ID, holder.Scope, exec_run, children)`.
- A schedule holder counts as refused unless `scheduleRewritable`.

Status mapping:

| Condition | Status |
| --- | --- |
| `Validate` error | `invalid_definition`, with its message |
| unknown id | `not_found` |
| `selfHolder`, or `refused > 0` | `holders_unreachable`, with `holders_refused` |
| stream too big | `body_too_large` (the `ActionDefinition` read limit is 512 KiB) |
| undecodable stream | `bad_body` |

Every message is cut to 256 bytes. A create with a non-zero `expect_revision`, or an edit with a zero one, is `invalid_definition`. `action_list` writes the `ActionListBody` on a send stream, as `handleRunnerKeys` does.

The children index comes from the rows' creator links.

`action edit` sends a whole definition:
- `--name` and `--description` default to the current record's values;
- the params and the template are given in full, as on `new`;
- `--revision` is required.
