# Credential tasks — a principal with no process

Date: 2026-11-21. Line references are to `main` at `0385ff87`.

## Why

An automation script outside the harness (cron on another host, CI, a webhook
receiver) should be able to call the harness — the motivating call is
`schedule run <id>` — holding only the authority that call needs. For a
schedule bound to task T that is `schedule_run` plus `resume_exact` over T,
once D16 lands; today it would also take full `resume` over T.

Today there is no credential to hand it:

- **Operator** (`server/psk.go:69-74`, binder keyed by the operator PSK) is the
  trusted root: `callerCaps` gives a connection with no principal task
  `Capability_All` (`server/capabilities.go:204-213`). Far too much for a
  script that fires one schedule.
- **Agent** (binder keyed by the task's ticket) is attenuable through the task's
  caps and scope, but the ticket is minted per `startSession`
  (`server/session_start.go:56-62`), revoked when the task ends
  (`server/boardkey.go`, `boardRevokeTask`), kept only in the in-memory board
  registry (so a server restart turns it into `BadTicket`), and keyed by
  `(runner identity, task id)` (`server/psk.go:131`). It belongs to one
  running agent process.

What is missing is a credential that is attenuable **and** outlives any process.

## Goals

- A **credential task**: a `TaskEntry` with caps, scope and a creator link like
  any task, but no runner, no process and no ticket. Its secret is an Ed25519
  private key held only by whoever it was issued to.
- An external process holding that key can open a TaskControl connection whose
  principal is the credential task, and every existing capability/scope check
  applies to it unchanged.
- Every credential **expires**: an expiry time is required at issue.
- It can be **revoked** before expiry.
- It is **visible** on CLI, TUI and WebUI: that it exists, what it holds, when
  it expires, when it was last used (operator, 2026-11-21: visibility is wanted
  regardless of the expiry question).

## Non-goals

- Agentboard access from a credential connection (see D10).
- Re-validating a key once it has stopped being the credential's key. Renewal
  and rotation go through resume (D18), which always takes a new key.
- A credential bound to a single verb or a single schedule beyond what caps +
  scope already express.

## Anti-goals

- **A credential connection that resolves to the operator.** `callerCaps` treats
  a zero principal as the root. If any path records a credential connection
  with a zero principal, a scoped credential silently becomes full operator
  authority. This must be impossible by construction and tested.
- **A secret at rest on the server.** The server stores public keys only. A copy
  of the server's state directory must not be enough to act as any credential.
- **A credential that keeps working after it ends.** A finished `TaskEntry`
  still carries its `Capabilities` (`callerCaps` reads them regardless of
  status), so expiry/revoke cannot rely on the status alone.

## Facts the design rests on

- Authority is keyed by `TaskEntry`: `Capabilities`, `Scope`, `CreatorTaskID`,
  `DelegateCaps`/`DelegateScope`, spawn limits (`server/taskstore.go:17-62`).
  `self` / `subtree` scope bases are positions in the creator tree
  (`authority/reach.go`). A principal without a `TaskEntry` cannot be scoped.
- After the handshake, a connection's principal is `h.principals[cid]`
  (`server/task_handler.go:295-340`), set from `AgentInfo.task_id` for
  `ClientKind_Agent`. Every cap check goes through `callerCaps(cid)`.
- `PskAuthRequest` is a `match role` union (`runner/protocol/message.bgn:181-187`).
  `AuthRole.runner` already verifies an Ed25519 signature over the transcript
  before looking the key up (`server/psk.go:280-299`, `cli.VerifyRunnerAuth`),
  so a not-enrolled answer only reaches a peer holding the private half.
- An unknown role decodes to no arm and is refused `no_identity`; the
  `harness-cli-from-a-tool` skill maps `no_identity` to "the server needs
  upgrading", which is what an old server would mean here.
- `TaskEntry` is persisted through the task WAL, so a credential task's row,
  public key and expiry survive a server restart without a new store.

## Design

### The credential task

`TaskKind.credential` (appended). New `TaskEntry` fields, persisted in the
`task_created` WAL record (appended fields — the WAL holds wire bytes, so this
is a disk-format change; an old server replaying a new WAL is the skew to
check):

- `CredentialPubKey [32]byte`
- `ExpiresAt time.Time`
- `LastUsedAt time.Time` — in memory, updated on each accepted handshake;
  persisting it is left to the builder (constraint: not one WAL write per
  handshake).
- `Name string` — optional operator label, shown in lists (a script's purpose
  is not recoverable from a hex id).

Status while live: whatever existing status the builder finds least disruptive
for a task with no runner (`Running` with no `AssignedTo` is the candidate; it
must not be picked up by the queue, the runner-death path, the agent resume
path, session open, exec, file transfer, or held-across-restart). Every task-status consumer
that assumes "Running ⇒ has a runner" must be found and taught the kind.

A credential task can never be opened, exec'd into, bound to a schedule as its
target, or assigned to a runner. Each refusal names the kind. Resume has its
own meaning for the kind (D18).

### Resume = re-key (D18)

Resuming a credential task registers a **new public key** and a **new expiry**
under the same task id — the credential analogue of an agent resume minting a
new ticket. Both are required; the request is refused without them.

- The previous key stops working at once, and every connection authenticated
  with it is closed (as D9). A key is never valid again once replaced.
- Works on an ended credential (revoked or expired: re-issue under the same
  identity) and on a live one (rotation).
- **Gated as issue, not as resume.** In an agent resume the new ticket goes to
  the runner's process; here the resumer supplies the key and so obtains the
  credential's authority. Plain `resume` keeps the recorded caps
  (`cli/verb/caps.go:103`), which would let a resumer acquire caps wider than
  its own. So credential resume requires `credential_issue` and that the
  resumer could issue a credential with the task's caps and scope now (the D13
  attenuation check against the recorded caps/scope, or against `--caps` /
  `--scope` when the resume narrows them). Resume therefore confers nothing a
  fresh issue would not.
- A credential cannot resume itself or another credential: it can never hold
  `credential_issue` (D14). Expiry stays mandatory.
- What the id keeps: caps, scope, name, the creator link, its children, and its
  attribution history (`resumed_by` in schedule history, the task list).
- The two ways of D3 apply: `--out` (generate) or `--pubkey` (register).

### Handshake (client)

`harness-cli` takes the credential from, in order: `--credential-file PATH`,
`HARNESS_CREDENTIAL_FILE`, `HARNESS_CREDENTIAL`. The value is
`<task-id-hex>:<seed-hex>`. When a credential is present the client sends
`AuthRole.credential` and never an operator binder. `HARNESS_SERVER_CID` and
`HARNESS_SERVER_PUBKEY` are used as today; the server signature on
`PskAuthResponse` is verified as today.

`whoami` on a credential connection reports the credential task id, its caps,
scope and expiry.

### Verbs

| Verb | Effect |
|---|---|
| `credential keygen --out FILE` | on the script's host: generate a key pair, write the seed (0600), print the public key (D3 way 2) |
| `credential new --ttl D [--name N] [--caps …] [--scope …] [--out FILE \| --pubkey HEX]` | issue. Without `--pubkey`, generate a pair and hand the seed over once — printed as `<task-id>:<seed>`, or written to `--out` (D3 way 1; D3a under an agent identity) |
| `credential rekey <id> --ttl D [--out FILE \| --pubkey HEX]` | resume = re-key (D18); also reachable as the generic resume of a credential task |
| `credential ls` | credential tasks in reach: name, id, caps, scope, expires, last used, status |
| `credential revoke <id>` | cancel (D11); also reachable as the generic task cancel |

Caps/scope flags reuse the spawn grammar. Exact verb names are the builder's,
following `cli/verb/table.go`.

### Surfaces

CLI, TUI and WebUI all get issue (both D3 ways), re-key, list and revoke (repo
rule: features span all three UIs). A seed generated at issue is handed over
once — shown with a copy affordance, or written to a file (CLI `--out`, WebUI a
download) — and is never written to a log, a history, or browser storage.
Credential tasks also appear in the ordinary task list, marked by kind, with
their expiry. `surface-parity-checklist` (items 1–39) is walked for the new
kind, the new fields and the new verb family.

### Wire

All appended: `AuthRole.credential`, `CredentialAuth`, `PskAuthStatus.revoked`,
`ClientKind.credential`, `TaskKind.credential`, `EndReason.expired`, the issue
request/response (public key in, task id out), the re-key request (task id,
public key, expiry in) and its WAL event, the `TaskInfo` fields for
expiry / last used / name. The runner decodes `PskAuthRequest` on its
data-plane listener; a credential arm there is refused. Run
`scripts/wire-skew-check.sh`.

## Approaches considered

- **A. Server-minted ticket, persisted.** One string to hand over, closest to
  the agent binder path. Rejected: the binder is an HMAC keyed by the ticket,
  so the server must store every ticket in plaintext; a leak of the state
  directory leaks every credential.
- **B. Ed25519, server keeps public keys only. Chosen** (operator,
  2026-11-21). Same one-string hand-over (the seed), nothing secret at rest.
  Wire cost equal to A: the agent arm assumes a runner id, so either needs a
  new arm.
- Rejected before choosing: a token entity separate from tasks (would have to
  fake a creator-tree position — a worse A/B), and a cap mask on operator
  credentials (the operator has no tree position, so scope cannot narrow it).
- Not a solution: an external script spawning a task and borrowing its env —
  the ticket dies with the process and with a server restart.

## Left to the builder

- The live status value and the full list of "Running ⇒ runner" consumers.
- Whether `LastUsedAt` is persisted, and how often.
- Verb names and flag spellings within the table conventions.
- The same site-by-site classification as D6 for `AuthRole_Client` checks:
  `pskGate.AllowsMessage` (`server/psk.go`) and `authorizeJoin`
  (`server/pubsub_authz.go`).
- A `ClientHello` claiming `ClientKind.credential` is refused, as one claiming
  `schedule` is (`server/task_handler.go:314-316`).
- Reads gated by scope alone (no cap bit) must also go dark for a credential
  that is not live — D8's `callerCaps` → `None` does not cover them.

## Testing

- A credential connection's principal is never zero: a table test over every
  path that records a principal, plus a server test that a credential holding
  only `schedule_run` is refused `schedule_edit` and every operator-only verb.
- Handshake: valid → ok; wrong key / unknown id / non-credential task →
  `bad_ticket`; past expiry → `expired`; revoked → `revoked`.
- D8: a connection opened before expiry is refused the first request after
  expiry even with the timer disabled.
- D9: revoke closes a live connection.
- Restart: issue, restart the server, the credential still authenticates; one
  expired while the server was down is ended at start.
- Refusals: open / exec / schedule-bind of a credential task.
- D18: resume without a new key or expiry is refused; after a resume the old
  key is refused and its live connection closed, the new key works with the
  same task id; a resumer holding `resume` but not `credential_issue`, or whose
  caps do not cover the credential's, is refused; resume of a revoked and of
  an expired credential both work.
- D16: `schedule run` of a schedule bound to T succeeds with `resume_exact`
  over T and no `resume`; `schedule edit` of it with only `resume_exact` is
  still denied `resume`; a pending_create run still needs `spawn`.
- D14: issuing with, or `set_caps` adding, `credential_issue` / `spawn` /
  `schedule_edit` on a credential task is refused.
- Dummy-harness E2E: issue from the CLI with `schedule_run` and `resume_exact`
  scoped to one task T, fire a schedule bound to T from a shell holding only
  `HARNESS_CREDENTIAL`, see
  `resumed_by` attributed to a credential in `schedule show`; revoke; the next
  call is refused `revoked`. TUI and WebUI issue/list/revoke checked live.
